# Groundwire v0.1 Durable Core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a self-hostable control plane where one demo agent Run survives a worker crash and an approval gate durably pauses until an API decision resumes it.

**Architecture:** FastAPI owns agent definitions, run records, and audit rows in Postgres. Starting a Run creates a Temporal workflow (`run-{run_id}`) on a Python worker. Activities persist status/audit back to Postgres. Approval is a Temporal signal; the workflow uses `wait_condition` so the pause outlives worker restarts. No auth, no dashboard, no model-router (those are later milestones).

**Tech Stack:** Python 3.12, FastAPI, SQLAlchemy 2 (async), PostgreSQL 16, Temporal Python SDK, pytest + pytest-asyncio, Docker Compose.

**Spec:** `Groundwire_PRD.md` (v0.1 — Durable core: G1, G2, FR1–FR9, FR13 as write-path only)

## Global Constraints

- License Apache 2.0; every dependency must be free for commercial OSS use.
- Python Temporal worker (not Go) — LangChain/CrewAI ecosystem fit.
- No OIDC/Keycloak, no Angular dashboard, no Go model-router, no Slack/email notifications in v0.1.
- Approvals in v0.1 are API-only (`approve` / `reject` / `edit`).
- Single default tenant UUID `00000000-0000-0000-0000-000000000001`.
- One demo agent type: deterministic `send_email` plan (no LLM calls — Groundwire does not provide prompting).
- Run statuses exactly: `planning`, `awaiting_approval`, `executing`, `completed`, `failed`, `rejected`.
- Workflow id is `run-{run_id}`; task queue is `groundwire-agent-runs`.
- `docker compose up` must bring up Postgres, Temporal, API, and worker.

## Review Focus

- Worker dies while a Run is `awaiting_approval`: after a new worker starts, the Run is still paused and a later approve/reject still completes it.
- Edit-and-approve must execute the edited params, not the originally planned params.
- Reject must not execute the gated tool and must set status `rejected`.
- Registering an agent with an empty name or empty `allowed_tools` is rejected with 422.
- Starting a Run for an unknown agent id returns 404, not a Temporal workflow.

**Interfaces:**
- Consumes: `RunWorkflowInput`
- Produces:
  - `ApprovalDecision(decision: str, edited_params: dict | None, actor: str)`
  - `PlanResult(summary: str, tool_calls: list[ToolCall])` where `ToolCall(tool: str, params: dict, rationale: str)`
  - `AgentRunWorkflow.run(input: RunWorkflowInput) -> dict` with `status` in `{completed, rejected, failed}`
  - `@workflow.signal approval_decision(decision: ApprovalDecision)`
  - `@workflow.query status() -> str` and `pending_action() -> dict | None`
  - `plan_run(input: RunWorkflowInput) -> PlanResult` — if payload has `to`/`subject`/`body`, one `send_email` tool call; else raise
  - `execute_tool(tool: str, params: dict) -> dict` — returns `{tool, params, result: "executed"}` (no real email)
  - `persist_run_progress(run_id: str, status: str, current_step: str | None, pending_action: dict | None) -> None`
  - `write_audit(run_id: str, tenant_id: str, event_type: str, actor: str, payload: dict) -> None`
  - Activity retry: maximum_attempts=3 on `execute_tool` only
  - If `tool` is in `approval_policy.require_approval_for`, wait for signal before `execute_tool`
  - `decision=="edit"` uses `edited_params` as the tool params
